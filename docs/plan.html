Direct Booking Check: the plan

Revision 3, 18 Oct 2026, before any code. Repo: /Volumes/asus/projects/hotel-direct-bookings. Research: /Volumes/asus/career-ops/research/hotelzify/ and findings.md. Sections marked with a green bar changed in this revision.

In one paragraph

A web tool where you type a US hotel's name and, in about 30 seconds, get a one-page check of the signs that guests are being pushed to booking sites like Expedia instead of booking direct, and what to fix first. It reads real public data: the hotel's Google listing and reviews, its Tripadvisor reviews and ranking, and its own website as loaded in a real browser. An AI reads the reviews and pulls out what guests love and what they had to work out for themselves, but every point it makes must quote a real review word for word, or code throws it away. It is a working, automatic version of the free report Hotelzify's founder hands out to US hotel owners at AAHOA events.

Decisions taken in revision 3 (18 Oct, evening)
  • Four sections added late on 18 Oct so the whole thing can be explained to anyone who asks: 12 testing, 13 usage, 14 measuring (no visitor analytics at launch; a per-run log line and a hand eval on 10 real hotels instead), 15 edge cases and hiccups, with three small spec additions proposed for a decision before handoff.
  • Two genuinely new parts, after the challenge "doesn't it just show data from other sites?": the gap check (questions guests raise in reviews, checked against the hotel's own website text) and the neighbour comparison (you against the 5 nearest hotels, counted, never named). Both are inferences no single site offers.
  • A direct booking score, 0–100, defined in code with stated weights, so it can be explained line by line. It is the thing people remember from the page.
  • Tripadvisor becomes optional to keep the two days: its client and tests stay, the pipeline wiring is "if time remains".
  • Report layout is now docs/report-infographic.html: score gauge, the "leak" flow, fix cards, gap table, radar comparison, phone-frame website check, praise with verified quotes.
  • Earlier revisions (kept): name "Direct Booking Check"; Next.js + TypeScript + Vitest on Vercel; handoff build; two audiences, one codebase; PageSpeed as the main website source; hotel matching by coordinates; top 3 fixes first.

Why not the other ideas

  • Finding each hotel's booking complaints in its reviews: killed by data. In 60 real reviews, booking and contact problems were rare (8–16%), and with only 5–8 reviews per hotel most reports would come out empty.
  • An AI phone agent: guests say "if an AI agent takes the call, I would hang up."
  • A commission calculator: Hotelzify already has one on its homepage.
  • A grounded reply assistant (the earlier concierge): no real data, and it doesn't touch how they sell.

3. System architecture: how a report gets made

Two pictures. The first is where things run: what lives in the visitor's browser, what runs on our server, and which outside services we call. The second is the order of work inside one report. Then the score formula, so it can be explained line by line.

3a. Where things run

Boundaries, left to right: browser → server is HTTPS to our own API routes; nothing in the browser holds a server key. Server → outside is the only place keys are used. Green = plain code that decides; blue = request handling; amber = secrets. There is no database: a report is computed and returned, and review text is never written anywhere (Google's terms, and nothing to leak).

3b. The order of work inside one report

Only one step uses AI, and its output passes through the quote check before anything downstream sees it. Everything that can be a rule is a rule. Wall time is bounded by PageSpeed (10–45 s), which is why the five jobs run together.

5. The AI part, and how it is kept honest

One AI call per report. It gets the 8 reviews (each with an ID) and must return, in a fixed JSON format:

  • Praise themes: a short name, the IDs of the reviews that mention it, and a word-for-word quote from each.
  • Things guests had to work out: same format.
  • Draft headline and ad lines built only from the praise themes.

The quote check (same idea as escalation-gate)

Code checks every quote is really in the review it cites (ignoring case and spacing). A theme whose quotes all fail is dropped. Theme counts ("3 of 8 reviews") are recomputed by code from the IDs that passed, never taken from the AI. Every dropped claim is logged, and those logs become the "where the AI went wrong" section of the write-up.

Why: free models (used for demos) invent more. A selling point a hotel can't back up is worse than no selling point.

What the check doesn't catch: a real quote filed under the wrong theme ("the parking was easy" under "parking confusion"). The write-up names this gap.

6. Security and reliability calls

The post says "US hotels trust us with guest and payment data". This tool handles no payments, but it handles other people's data and keys, so each call is made on purpose:

CallWhy
Review text is never stored. Fetched live, used for one report, then gone. Only Google place IDs may be kept.Google's Places terms. Also: no database of guest-written text to leak.
Reviewer names shown only as Google requires (attribution beside each Google review), never logged.Reviewers are people; keep personal data to the minimum.
A viewer's own OpenRouter key is used once and never kept. It lives in the browser tab (sessionStorage), travels only inside the report request, is used for that one call on the server, and is never written to a log, a database or an error message. A test asserts the response never echoes it.The browser cannot call OpenRouter directly without exposing the request shape and the model prompt, so the server makes the call; the rule is then "hold it for one request, write it nowhere". (Corrected 18 Oct: an earlier line here said the key never touches the server, which was wrong.)
Our API keys stay server-side in environment variables, never sent to the browser.Stops key theft and surprise bills.
The fallback fetch is locked down: http/https only, blocks private and internal addresses, 8-second timeout, 2 MB cap, at most 3 redirects.Fetching a URL someone else controls is a classic way to attack a server (SSRF).
The real spending guard is a hard daily quota on the Places key, set in Google Cloud. Per-visitor rate limiting in the app is best-effort only, because Vercel runs many short-lived copies of the server and an in-memory counter resets with each one.A link shared on X can't run up the Google bill, even if the app-level limit is bypassed.
Each source can fail alone. Timeouts on every call; the report shows "not available" for that section instead of failing.One slow API shouldn't kill the report.
Review text is treated as data, not instructions in the AI prompt, and the output must match a strict format.A review saying "ignore your instructions" shouldn't change the report.

8. The 2-day build

Bottom up: each layer is tested before the next starts. Codex builds via handoff; spec/site.md and the failing tests (11 files) are committed first. Step numbers match the spec.

Day 1: data and logic, no UI

  1. Quote check pure logic
    Verify quotes against reviews; recompute counts; log drops.
  2. Website checks from Lighthouse data pure logic
    Speed, HTTPS, viewport, booking engine from network requests, "Book now", tap-to-call.
  3. Safe fetch
    The locked-down URL fetch (private networks blocked, redirects re-checked, size and time caps).
  4. Gap check pure logic
    Page text extraction, topic keywords, "does the site mention it".
  5. Neighbour comparison
    Nearby search without reviews; averages and ranks.
  6. Score pure logic
    The four sub-scores and the weighted total (3c).
  7. Sources
    Google, PageSpeed, Tripadvisor clients and the fixture mode, tested on recorded responses.

Day 2: joining, AI, page, ship

  1. Report builder
    Findings, fixes, top 3, score, missing sections, the partner flag.
  2. AI layer
    One interface, strict JSON, fake + OpenRouter clients.
  3. Pipeline
    The order in 3b, with every failure contained.
  4. API routes and rate limit.
  5. Pages
    Search → pick → report, laid out like the infographic mock-up.
  6. Docs and optional extras
    README; then Tripadvisor wiring, then the claude -p wrapper, only if time remains. Then you run it on real hotels.
If day 2 slips, cut in this order: Tripadvisor wiring → viewer's-own-key mode → claude -p wrapper. Never cut the quote check, the gap check or PageSpeed.

11. Risks and weak spots

  • They may already have this internally. Say "a working, automatic version of the report you hand out", never "new".
  • Posting real hotels' weak spots on X is unfair to them. On X, show the tool and your process, not a named hotel's bad score. Real reports go only privately.
  • No Hotelzify name or branding on the public site. "Built by Deepak R, not affiliated with any company." The founder's version is a flag, not a public page.
  • Google's terms on sending review text to a third-party AI are unclear. Check before going public; if it's a problem, the public demo runs the AI step on Tripadvisor reviews only.
  • Website checks can still miss things on unusual sites. The report says "not found", never "missing".
  • Booking engine on another domain is also true of Hotelzify's own hotels (bookmystay.io). Raise it in the CEO call as an insight, not in public as a criticism.
  • Hotelzify's own Trustpilot is 2.5, partly guests distrusting the .io domain. Same: CEO call, not public.
  • 2 days is tight. Cut order is in section 8.

12. How it is tested

The tests were written before the code, and they are the contract: Codex (a different model) builds until they pass, and I review against them. There are 11 test files, about 95 cases, all failing today with "cannot find module", which is the right reason: the modules do not exist yet. Nothing may be stubbed to make them pass early.

Three kinds of test, and no test ever touches the network:

  • Pure-logic tests feed a function a value and check the answer. Quote check, website checks, gap check, benchmark, score, report builder.
  • Recorded-response tests give a source function a fake fetch that returns a saved Google / PageSpeed / Tripadvisor reply from tests/fixtures/, and check the request we sent (URL, headers, field mask) and how the reply was normalised.
  • Fixture-mode tests run the real API routes with SOURCES_MODE=fixture LLM_MODE=fake: every source returns its fixture and the AI returns a scripted answer. The same mode drives the preview screenshots, so the page can be reviewed with no keys and no spend.
Test fileStepWhat it proves, in plain words
quotes.test.ts1A quote counts only if it is really in the review it names, ignoring case, spacing and curly quotes. Invented quotes and unknown review ids are dropped and recorded. Counts are recomputed; a review quoted twice counts once; themes sort by count.
website.test.ts2The booking engine is named from its domain (ten vendors at least, Hotelzify's among them), analytics and fonts are ignored, a booking path on the hotel's own domain is "on own domain". "Book now" is found loosely but "Facebook" and "guestbook" do not count. The raw-HTML fallback finds the same signals.
safeFetch.test.ts3Private and internal addresses are refused before any request is made; every redirect hop is re-checked; it gives up after 3 redirects, cuts bodies at 2 MB and times out.
gaps.test.ts4Page text comes out without scripts and tags, every topic has keywords, a theme maps to a topic, and each guest question is marked answered / not answered / unknown (unknown when there is no page text).
compare.test.ts5Nearby search asks for lodging within 1.5 km and never asks for reviews; the hotel itself is dropped; averages and ranks are right; no neighbours gives null, not a crash; a metric the hotel lacks is skipped.
score.test.ts6Each sub-score line by line, the floors at 0, the fixture total of 54, the re-spread of weights when a sub-score is missing, and "null only when nothing could be scored".
sources.test.ts7The exact requests to Google, PageSpeed and Tripadvisor; review ids g-1… and ta-…; author attribution kept; a missing key fails with the variable's name; a non-2xx reply fails with the status code; name matching picks the best name, not the nearest place.
report.test.ts8No percentages anywhere, never the word "OTA", "not found" rather than "missing", top 3 ranked by severity then by review support, partner product names only for the partner audience, an unanswered question becomes a high-severity gap finding, the neighbour average appears in the evidence, the score is carried, and a missing source marks its section unavailable instead of failing.
llm.test.ts9The prompt includes every review by id and frames review text as data; the parser accepts the fixed JSON shape (with or without a code fence) and rejects prose or missing keys; one retry on bad output, then a clear failure; no model call when there are no reviews; an OpenRouter error never contains the key.
pipeline.test.ts10Everything is joined into one report; neighbours never get a reviews fetch; the report still comes out when the neighbour search, Tripadvisor or PageSpeed fails; PageSpeed failure falls back to the plain page; Google failure fails the run; the AI failing twice marks only the AI section unavailable.
api.test.ts11Search works in fixture mode and rejects an empty query; the report route builds a full report, adds product names for the partner audience, rejects a missing place id, accepts a viewer's key only in the body and never echoes it, and returns 429 past the limit. The limiter allows n hits, refuses, then resets.

"Done" is checked three ways: npx vitest run passes with no skips and npx tsc --noEmit is clean; the fixture preview shows "Harborside Inn" with the score 54/100, the parking gap in the top 3, the neighbour comparison and the praise quotes; and one live run on a real hotel with real keys succeeds. What tests cannot prove: that Google's real reply still has the shape we recorded, or that a real model behaves like the scripted one. That is what the live runs in section 14 are for.

13. How it is used

By a visitor

  1. Open the site, type a US hotel's name. A list of matches appears (name and address, so two hotels with the same name can be told apart). Pick one.
  2. Wait. The page shows a loading state for 10–60 seconds, because PageSpeed is loading the hotel's website and five neighbours' websites in a real phone browser.
  3. Read top down: the score and what it is made of, where the leak is, the three fixes to do first, then the detail sections. Everything is written for the owner, not for a developer.
  4. Optional: paste your own OpenRouter key on the search page to use a better model. It is kept in your browser tab, sent once with the request, and never saved.

14. How to measure it, and what "analytics" means here

There is no visitor analytics on the public page at launch. No tracking script, no cookies, no database. That is deliberate: the page handles other people's reviews and, sometimes, a viewer's own API key, and the fewer third parties on it the easier it is to explain. What we measure instead is in three layers.

14a. Does it work? (per run)

Each report already knows what went right and wrong: which sections came back, how many quotes the AI invented, how long it took. The plan is one structured log line per run, visible in Vercel's logs, containing only these numbers and never a key, a review text or the viewer's IP:

NumberWhat it tells youHealthy looks like
Run succeeded / failed at GoogleWhether the place lookup is reliableFails only on bad place ids

Website source: lighthouse or htmlHow often PageSpeed timed out and the fallback ranFallback on fewer than 1 in 5
Quotes dropped / quotes offeredHow much the model invents; the honesty rateFree model under 30 percent dropped; a good model under 10
Wall timeWhether the page is tolerableUnder 60 s
Neighbours foundWhether the comparison has a basis3 or more in a town, 5 in a city

This log line is in the spec since 19 Oct (step 10, "Run log", with tests in tests/pipeline.test.ts). It is the only way to answer "how often does the AI invent quotes" with a number in the interview.

14b. Is the report right? (hand check on real hotels)

Tests prove the code does what the spec says; they cannot prove the spec is right about hotels. So after the build, you run it on 10 real US independent hotels of different sizes and check each finding by hand, the way you did the 15-case eval for escalation-gate:

The results table goes in the README under "Results" and in the Hotelzify write-up. No invented numbers; if a run was bad, it is in the table.

14c. Did it do its job?

For the job: a reply from the founder, a call, and whether the interview questions about the system can be answered from sections 3, 5 and 6 without looking. For Hotelzify as a product: of the 3–5 owners whose reports you send, how many would take a call after reading it. That is the only metric the founder cares about, and it is measured by asking.

14d. Cost per report

One Places text search, one Places details call (the one with reviews, the expensive tier), one nearby search, up to six PageSpeed calls (free), one OpenRouter call (free model or the viewer's key). Three paid Google calls per report; the price per call is on Google's current Places pricing page and changes, so the README quotes the call count, not a rupee figure. The hard daily quota on the Places key is the cap; set it to the number of reports you are willing to pay for in a day, and no shared link can exceed it.
