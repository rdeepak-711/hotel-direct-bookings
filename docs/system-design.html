2. Architecture

Three zones: the visitor's browser, our server (Vercel functions), and the outside services. The server is the only thing that talks to the outside. There is no database.

Why serverless and no database, said once.

Google's policy forbids storing review text, the report is a point-in-time check, and a store of guest-written text would be one more thing to leak. The cost is that nothing is remembered between runs beyond ten minutes, and the in-memory limiter and cache reset whenever Vercel spins a new instance. That is why the real cost guard is the Google Cloud quota, not app code.

→ 200 { results: [{ placeId, name, address, rating, reviewCount }] }
→ 400 when q is empty

body: { placeId: string, audience?: "public" | "partner",
        partnerToken?: string, byok?: { apiKey: string, model: string } }
→ 200 Report (JSON; never contains an API key or a full review text)
→ 400 without placeId
→ 429 when the visitor exceeds REPORTS_PER_VISITOR_PER_HOUR (default 10)

6. Data: stored, cached, passed through

Stored

Nothing. No database, no file writes, no analytics. The only persistent output is the one-line run log in the platform's log stream, and it carries no identifiers.

Cached, 10 minutes, in memory

PageSpeed raw results keyed by URL and the nearby list keyed by place id. Both are our derived numbers plus place ids, which Google allows. Never place details, reviews or AI output.

Passed through and dropped

Review text (used for one prompt and one quote check), the viewer's own API key (one request, never logged), full page HTML (reduced to text, then dropped).

The shared types in lib/types.ts are the data model: Hotel and Review in, WebsiteChecks, Gap, Comparison, VerifiedThemes and Score in the middle, one Report out. The Report is the whole contract with the page; the page computes nothing.

9. Scale and cost

What it is built for

Tens of reports a day from a shared link, plus a handful of runs for the Hotelzify challenge. At that volume the design is right: serverless scales to zero, the cache saves the repeat lookups, and the quota caps the bill.

Cost per report, today

ItemPer reportNote
Google Places1 text search (on the search page) + 1 place details with reviews + 1 nearbyPlace details with reviews is the priced call. The daily quota bounds it.
PageSpeed1 + up to 5Free with a key; throttled hard without one.
OpenRouter1 completion (2 on retry)Free model on the demo key; the viewer's key otherwise.
ComputeOne function invocation up to ~60 sMostly waiting on the network.

What breaks first, and the fix at each step

AtWhat breaksChange
~50 reports/day on the demo keyOpenRouter free-model cap.One-time $10 credit raises it to 1,000; or push viewers to BYOK.
Many instancesIn-memory limiter and cache are per instance, so limits are leaky and cache hits drop.Move both to a shared store (Vercel KV or Upstash Redis): same interfaces, TtlCache and RateLimiter get a backing store.
Long runsA 60 s synchronous request is fragile: client timeouts, no progress, no retry.Make the report asynchronous: POST returns a job id, work runs in a queue (Vercel Queues or a worker), the page polls or streams sections as they finish. The pipeline's per-section independence already fits this.
Batch mode (50 hotels)300 PageSpeed runs and 50 reviews fetches at once.Queue with concurrency limits per external service; results persisted as derived numbers and place ids only, never review text.
Google quotaThe hard quota rejects the fiftieth-plus details call of the day.Raise with billing alerts; cache the derived listing fields (not reviews) per place id for a day.

open None of the above is built. The honest answer in an interview: "v1 is synchronous and in-memory on purpose, and here is the path to async and shared state when volume asks for it."

10. Observability

One structured log line per run, written by runCheck exactly once, success or failure:

{ "event": "report_run", "ok": true, "failedAt": null, "wallMs": 41230,
  "sections": { "website": true, "comparison": true, "ai": true, "tripadvisor": false },
  "websiteSource": "lighthouse", "siteText": "read", "pagesRead": 3,
  "quotesOffered": 11, "quotesDropped": 1, "neighbours": 5 }

It answers the three questions that matter for the job: how often does PageSpeed fall back, how often does the AI invent a quote, how long does a run take. It deliberately omits keys, review text, the hotel name, the place id and the IP, so the log can be shared.

open No metrics dashboard, no tracing across the five parallel jobs, no alerting. Vercel's log stream is the only consumer. A hand check on 10 real hotels, recorded in the README, is the planned quality measurement.

11. Frontend

Two Next.js pages, both rendering what the server returns.

  • /: search box → GET /api/search → results list → click → /report?placeId=…. Optional field for the viewer's own OpenRouter key, kept in sessionStorage, sent only in the report POST body. Footer states the tool is unaffiliated and stores no review text. Works at phone width.
  • /report: loading state (PageSpeed can take 30 s) → half-ring gauge with three sub-scores → top 3 fixes → listing → website → gap check → neighbour comparison → praise with attributed quotes and Google Maps links → headline and ad lines → footnote. ?partner=<token> is forwarded as partnerToken; the server decides. Layout reference is docs/report-infographic.html.

No state management library, no client-side computation of the score, no tracking script. partial No streaming: the page waits for the whole JSON.

12. The interview sheet

The questions a system design round would ask about this, and the answer v1 has. Say the open ones as open.

QuestionAnswer
Walk me through a request.Section 3. Place lookup is the only fatal step, five jobs in parallel, then gaps, score, report, one log line.answered
Where is the database?There isn't one, by policy and by choice. Ten-minute cache of derived numbers only.answered
How do you stop the model from making things up?Code verifies every quote as a substring of the cited review and recomputes counts; the model never writes a finding or a score.answered
What is genuinely new, not a dashboard?Two cross-source inferences: the gap check and the neighbour comparison.answered
How do you handle rate limiting on serverless?Best-effort in-memory limiter, acknowledged as leaky; the real guard is the Google Cloud quota. Next step is a shared store.answered
What about SSRF, you fetch arbitrary URLs?safeFetch: scheme, private ranges, every redirect hop, 3 hops, 8 s, 2 MB. DNS rebinding is the known partial.answered
Why is the response 40 seconds?PageSpeed. Everything else is parallel. The async-with-polling design is the next step and the pipeline is already section-independent.answered
What happens when PageSpeed is down?HTML fallback with a neutral starting score; logged as websiteSource: "html".answered
How do you keep the Google bill bounded?Quota, limiter, cache, and never fetching neighbour reviews.answered
Why those score weights?Judgement, in code, explainable line by line; not measured against bookings, and the README says so.answered
How do you test it?Fixture sources and a fake LLM make every run deterministic; 11 test files written before the code.answered
Why detect the booking engine instead of testing the booking flow?Driving a third party's engine is the scraping problem again, adds a minute, and the question is "is there a direct path". Day-60 feature with consent.answered
How would you scale to 50 hotels per request?Queue, per-service concurrency limits, derived-only persistence. Designed, not built.partial
Authentication and multi-tenancy?None. Public tool; one shared partner token. A product would need accounts and per-tenant quotas.open
Monitoring and alerting?One log line per run. No dashboard, no alerts, no SLO.open
CI/CD?Vercel deploy on push. No CI running the tests before deploy is specified.open
Idempotency and retries?Reports are idempotent by nature (same input, same report within the cache window). No retry with backoff on outbound calls.partial
How accurate is the gap check?Keyword topics with excludes; "street noise" gets no topic; the 200-character threshold is a guess. The 10-hotel hand check is where it gets measured.partial

13. Open gaps, in one place

  • No authentication, no accounts, no per-tenant quotas.
  • No CI step that runs the tests before a deploy.
  • No alerting, no dashboard, no SLO. The log line exists; nobody reads it automatically.
  • No retries with backoff or circuit breaker on outbound calls.
  • No DNS-level check in safeFetch (rebinding).
  • No request schema validation beyond the two required fields.
  • No security headers specified (CSP, HSTS beyond the platform default).
  • Limiter and cache are per instance; a shared store is the next step.
  • Synchronous 60-second request; async job with polling or streaming is the next step.
  • Batch mode designed, not built.
  • Dependency audit not part of the build.
